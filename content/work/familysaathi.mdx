## What it is

FamilySaathi is a service I&rsquo;m starting in Meerut and the Delhi-NCR corridor: verified drivers for your own car, plus trusted day-to-day family assistance. I designed and built the whole thing — and it&rsquo;s the clearest example in my portfolio of shipping deliberately in two phases: prove the idea cheaply first, then build the real engineering once it&rsquo;s worth it. It&rsquo;s live and entirely mine to run: design, code, database, and deploys.

## Phase 1 — prove demand, spend nothing

The product didn&rsquo;t exist in software yet, so the first job wasn&rsquo;t a booking engine — it was finding out whether anyone wanted this. I shipped a **static site with no framework and no build step**: one `index.html`, one stylesheet, one vanilla-JS file. Enquiries went straight to WhatsApp via pre-filled messages, so there was no backend to run or secure. It cost nothing to host and went live fast.

The one piece of foresight that made Phase 2 cheap: even in the static version, the content that would eventually come from a database — the driver profiles and the FAQs — already lived in **typed arrays in a single source-of-truth file**, never hard-coded into the markup. I built Phase 1 knowing exactly how it would grow.

## Phase 2 — the full-stack rebuild

Once the shape of the thing was right, I rebuilt it end to end into a **Next.js 15 (App Router) app in TypeScript**, backed by **Prisma and Postgres (Supabase)** — while keeping the Phase-1 design pixel-for-pixel by porting the stylesheet verbatim. The static sections became server components; the interactive parts (theme toggle, booking widget, driver search &amp; filter, FAQ accordion, enquiry form) became focused client islands.

The decision I&rsquo;m most pleased with is the **data layer with a seed-data fallback**. Drivers and FAQs are read from the database at request time, but if there&rsquo;s no `DATABASE_URL` — or a query fails — the same code falls back to the built-in seed arrays:

```ts
export async function getDrivers(): Promise<Driver[]> {
  if (prisma) {
    try {
      const rows = await prisma.driver.findMany({
        where: { active: true }, orderBy: { order: 'asc' },
      })
      if (rows.length) return rows.map(toView)
    } catch (err) {
      console.error('[data] DB error — using seed data:', err)
    }
  }
  return seedDrivers // same content that seeds the DB, so nothing ever renders empty
}
```

That one pattern means the app **builds and runs identically with or without a database** — it deploys and renders on day one, then becomes fully DB-driven the moment the connection string is set, with no code change. The enquiry form now does both jobs: it `POST`s to an `/api/enquiry` route that validates the input and saves a real lead to Postgres, *and* still opens the pre-filled WhatsApp chat. Business details — WhatsApp number, phone, email, canonical URL — moved out of the code into `NEXT_PUBLIC_*` env vars, so going live is a config change, not a commit.

**Stack:** Next.js 15, React, TypeScript, Prisma, Postgres (Supabase), Vercel.

## What shipping it actually taught me

The rebuild deployed cleanly through a couple of real-world snags worth noting, because they&rsquo;re the kind of thing that only shows up in production. The Vercel project had been created for the static Phase-1 site, so its framework preset was still &ldquo;Other&rdquo; — the Next.js build compiled fine but then failed looking for a static output folder, until I switched the preset to Next.js. And Vercel&rsquo;s security scanner flagged a React Server Components CVE in the pinned version, which I took as an auto-patch bumping to the fixed release. Deploys run off Git now, so every push to `main` ships.

## What I'd change next

The foundation is built for where this goes: customer accounts, a real booking workflow with status tracking, and an admin dashboard so the drivers, FAQs and incoming enquiries can be managed without touching code — the schema and data layer are already shaped for it. The near-term list is the honest launch work: swap the placeholder contact details and pricing for the real business values, wire the production Supabase project, and add a custom domain. Phase 1 told me the idea was worth building; Phase 2 is the thing I can actually grow.
