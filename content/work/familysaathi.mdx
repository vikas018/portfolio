## What it is

FamilySaathi is a service I&rsquo;m starting in Meerut and the Delhi-NCR corridor: verified drivers for your own car, plus trusted day-to-day family assistance. This is the site that turns a visitor into an enquiry. I designed, built, and shipped it end to end — it&rsquo;s a Phase-1 marketing and lead-generation site, live, and entirely mine to run.

## The constraint

The product doesn&rsquo;t exist in software yet — the first job isn&rsquo;t a booking engine, it&rsquo;s proving demand. So the site had to go live fast and cost nothing to run, while still looking like a real business people would trust with a driver for their family. Enquiries had to land somewhere the owner actually checks — a phone and WhatsApp — not a dashboard no one watches. And whatever I built first couldn&rsquo;t become a dead end: once there are real drivers, real bookings, and a backend, the site has to grow into that, not be thrown away.

## The decision

**Ship a static site with no build step and no framework — plain HTML, CSS, and vanilla JavaScript.** For a Phase-1 site whose only job is to explain the service and capture enquiries, a React or Next.js setup is weight I&rsquo;d be paying for nothing. So the whole thing is one `index.html`, one stylesheet, and one JS file. Enquiries go over WhatsApp: the booking widget and contact form build a pre-filled message and hand it to the shop&rsquo;s chat, so there&rsquo;s no backend to run or secure. Crucially, the content that will later come from a database — the driver profiles and the FAQs — already lives in typed arrays in one file, as a single source of truth. That one decision is what lets this grow into a Next.js app later instead of being rewritten.

## How it's built

A single static page in HTML5, CSS3, and vanilla JavaScript — no framework, no bundler, no dependencies. The JavaScript drives everything interactive: a light/dark theme toggle (respecting the system preference), a mobile menu, a hero booking widget that assembles the enquiry, a driver search-and-filter list, an FAQ accordion, and WhatsApp links wired across the page. It deploys on Vercel.

Every enquiry is just a pre-filled WhatsApp message — no cart, no backend:

```js
// Each enquiry becomes a pre-filled WhatsApp message to the business.
// No form backend, no server to run or secure.
function waLink(msg) {
  return "https://wa.me/" + WA_NUMBER + "?text=" +
    encodeURIComponent(msg || ("Hi " + BRAND + ", I'd like to know more."));
}
```

The part I was most deliberate about is the data. The driver cards and FAQ entries read from plain arrays declared at the top of the script, so the content changes without touching markup — and when there&rsquo;s a real backend, those same arrays become an API or CMS call. The static sections map one-to-one onto React components, so the migration path is a refactor, not a rebuild.

**Stack:** HTML5, CSS3, Vanilla JavaScript, Vercel.

## What I'd change

This is Phase 1 on purpose, and it&rsquo;s honest about that: the phone number, WhatsApp number, email, and pricing are still placeholders marked as TODOs, waiting on the real business details. Once demand is proven, the plan I built toward kicks in — move it to Next.js, turn the driver and FAQ arrays into real data behind an API, and replace the WhatsApp-only flow with a proper `/api/enquiry` endpoint so leads are captured and tracked rather than living in a chat thread. The static site isn&rsquo;t the destination; it&rsquo;s the cheapest possible way to find out whether the destination is worth building.
